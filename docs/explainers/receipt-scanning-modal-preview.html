PET-59 · Frontend · Proposal

Scanning a receipt into the Add transaction modal

The existing modal gains four things and loses none: two scan controls, a disclosure line naming what leaves the device, a dismissible loading overlay, and a note saying which fields a scan could not fill. Every control below is stock daisyUI on the app's own light and dark themes, so the page follows your system setting and the toggle above overrides it.

What is added to the modal

  • Two controls on a phone, one on a desktop

    Camera for one photo, upload for up to four images - or one PDF.

  • A disclosure line

    Names what leaves the device, at the moment of action rather than in Settings.

  • A dismissible overlay

    The scan can always be abandoned, and a timeout sits behind it.

  • A missing-fields note

    Says which fields to photograph again instead of failing silently at submit.

The control row differs by device

capture="environment" is a hint desktop browsers ignore, so on a laptop the camera control is not merely redundant - it is the same file picker as the one beside it, under a label promising a camera. It is hidden there by @media (pointer: fine), which asks about the input modality rather than sniffing the user agent. Written as a hide on fine rather than a show on coarse deliberately: a device reporting neither - a headless browser, some kiosks - then keeps the camera, and a redundant button is a far cheaper failure than a phone that loses the one control this ticket exists for. Both rows below are drawn unconditionally so both are visible from one machine.

1 · Before a scan

Live - adapts to this device

The form is unchanged below the fold. What is new sits above Amount, because scanning is how the fields get filled - putting it under them would ask the user to scroll past the work to find the shortcut. This plate carries the real media query, so on a laptop it shows one control and on a phone two.

Add transaction

What you upload, your recent merchant names and your category names are sent to Google Gemini to read the receipt, and may be used to improve their models. Nothing is stored. Up to 4 photos or one PDF, all treated as pages of one receipt.

3 · After a scan

Partial extraction

The scan filled Amount, Merchant and Date. It did not find a category, so that field is named in the note rather than guessed at - a wrong category renders as a confident answer, where a blank one asks. The Note field was typed by hand before scanning and is left alone: the merge tracks which fields the user touched, not which are empty. Both labels change, because a second scan fills gaps rather than starting over.

Every outcome has its own line

Nine endings, each with copy of its own. A generic "something went wrong" would tell a rate-limited user to retry immediately and a user with scanning switched off to keep trying forever. The status column is what the backend answers.

Status Outcome What the user reads
200 Filled, some missing Couldn't read the category. Pick one below, or photograph the rest of the receipt.
200 Nothing extracted Nothing readable in that photo. Try again with the whole receipt in frame.
503 Scanning unavailable Receipt scanning is switched off right now. You can still add the transaction by hand.
429 Rate limited You've scanned a lot in a short time. Wait a minute and try again.
504 Timed out That scan took too long. Try again, or add the transaction by hand.
400 Upload rejected That file isn't a receipt we can read. Use photos, or a single PDF.
400 PDF sent with other files Send a PDF on its own - it already holds every page.
413 File too large That file is too big. Photos can be up to 1.5 MB after compressing, a PDF up to 4 MB.
- Compression failed This phone saves photos in a format the browser can't read (HEIC). Use Scan receipt, or convert the file first.

Open for a designer

  1. 1 "Upload receipt", not "receipts". Picking several files at once is supported - up to four - but they are read as pages of one receipt and become one transaction. The plural would promise a batch import the modal cannot perform, where several receipts sent together are merged and all but one silently lost.
  2. 2 Whether the camera should be hidden at all, or just be the only control everywhere. One "Upload receipt" on every viewport is one fewer control and one fewer conditional - the OS picker offers the camera anyway - but it buries the ticket's actual subject two taps deep on a phone.
  3. 3 Where the controls sit. Drawn above Amount, inside a tinted panel with the disclosure. The alternative is a single icon button in the header, which is quieter but leaves the disclosure homeless.
  4. 4 How loud the disclosure should be. It is text-xs muted here. It names a real transfer of financial data to a training-enabled endpoint, so quieter may be too quiet.
  5. 5 Whether the unfilled field earns select-warning. It marks the one control the user must still touch, but warning colour normally means invalid, and nothing here is invalid yet.
