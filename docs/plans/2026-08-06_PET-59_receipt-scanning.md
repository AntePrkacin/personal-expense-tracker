# PET-59 — AI Receipt Scanning

[PET-59](https://decode.atlassian.net/browse/PET-59) — `[FE/BE] Build AI Receipt Scanning via Mobile Camera`

Base branch is `main`.

## Why

Typing out transactions manually is tedious, especially on mobile. Modern Vision models can reliably extract the merchant, amount, category, and notes from a simple photo of a receipt. This feature allows users to tap a "Scan Receipt" button in the Add Transaction modal, take a photo with their phone camera, and have the transaction form automatically populated. This dramatically reduces friction and creates a "wow" factor for the application.

## Decisions

**Do not persist images.** Storing receipts would require significant infrastructure (S3/R2) and introduce data privacy and retention complexities. The image will be processed entirely in-memory, sent to the AI for extraction, and then immediately discarded.

**Personalized Category Matching via Prompt.** The database requires a strict ID for `categoryId`. The AI cannot guess this ID. The backend must fetch the user's categories and inject them into the prompt (e.g., `[{"id": "...", "name": "Food"}]`). Additionally, to improve accuracy and enable fuzzy matching, the prompt will include an array of the user's merchants from the past year. Each merchant object will list the categories associated with it and the transaction counts for each category. This allows the AI to correctly map generic or misspelled receipt names (e.g., "WM SUPERCENTER") to the user's specific habits.

**The merchant history is capped at the top 50 by transaction count, and the cap is the point rather than a detail.** "Every merchant from the past year" is unbounded: `backend/src/scripts/seed-showcase.ts` alone produces a history that would put hundreds of rows into the prompt on *every* scan, paid for three times over - in latency, in tokens, and on the free tier in exactly the data Google retains. A long tail of one-off merchants also cannot help fuzzy matching, because a merchant seen once carries no habit to match against. The query therefore orders by count descending and takes 50, and the number lives in one named constant so it can be tuned against a real prompt rather than rediscovered.

**One scan produces one transaction, and "multiple images" means multiple pages of one receipt.** The modal writes a single `POST /transactions`, so every image in a scan request is treated as pages of the *same* purchase and synthesized into one extraction. Selecting photos of two different shops is therefore a user error the feature does not detect, and the copy must say "pages of one receipt" rather than "receipts" so nobody expects a batch import. Scanning several distinct receipts into several transactions is a genuinely different feature - it needs a review queue, N draft rows and a bulk write, none of which the modal can express - and it goes to `docs/TODO.md` rather than being smuggled in behind a `multiple` attribute. **This resolves a contradiction in the first revision of this plan**, which offered to "select multiple receipts at once" while every other line described one form and one submit.

**A model that returns the same id it was given, or none.** The backend validates the returned `categoryId` against the user's live categories and **drops** an id that matches none, reporting the field as missing. It deliberately does not fall back to `Uncategorized`: that would render as a confident categorization and quietly mis-file the expense, where a missing field asks the user to pick. Left unvalidated, a hallucinated id reaches the modal's `<select value={values.categoryId}>`, matches no option so the control shows nothing, and submission then fails as a 404 mapped to `categoryMissing` - a failure whose cause is invisible from the screen.

**`date` and `amount` are validated too, and for the same reason `categoryId` is: the form's fields are not the DTO's types.** Validating one of three invented values and trusting the other two only moves the failure. `date` must be a real ISO calendar date, because `transactionForm.ts`'s `isDateValid` defers to `lib/date.ts`'s `partsFromIso`, which answers `null` for anything that is not `YYYY-MM-DD` - so a model answering `08/09/2026` or a well-formed-but-impossible `2026-02-30` lands in the field, fails at submit with `MESSAGES.date`, and never appears in `missing` where the user could act on it. `amount` is the subtler one: `TransactionFormValues.amount` is documented in that same file as **a display string, not a number**, and its canonical writer is `toTransactionFormValues`'s `formatAmountInput(transaction.amount.toFixed(2))`. A JSON `12.5` written into the field as `"12.5"` therefore diverges from every other path into that control. The Server Action normalizes through the same call, so a scanned amount and an edited amount are byte-identical in the DOM.

**Privacy, the free tier, and what a Google AI Pro subscription does not buy.** Google AI Pro applies to the AI Studio *web interface*; the plans documentation is explicit that "Direct use of the Gemini API (such as using API keys or external applications) is billed and managed separately". An API key is on the Paid tier only when its Cloud project has an active billing account, and the free tier's terms are unchanged by any consumer subscription: prompts - here the receipt image and up to 50 of the user's merchant names - are used to improve Google's products. **This project stays on the free tier deliberately**, because the quota is ample for a portfolio app whose accounts are all test accounts, and because a $10 prepay to buy a training opt-out for seeded data is not a trade worth making. The consequence is that the disclosure below is mandatory rather than courteous. Migrating to the paid tier is the *only* mechanism that turns training off, so it goes to `docs/TODO.md` against the day this app has a real user.

**The disclosure is on-screen copy in V1, not a setting, and that is a scope decision rather than a preference.** The honest version of the paragraph above has to be visible at the moment of action, because the first scan sends both the photo and a year of the user's merchant names to a training-enabled endpoint. A real opt-in belongs in Settings, and Settings' `<main>` is not built - so a toggle would mean a new profile column, a migration, an `api:sync` and a screen to host it, all before the feature works at all. V1 therefore renders a short line beside the scan buttons naming what leaves the device (the images, and up to a year of merchant names for matching) and what is not kept (the images). The toggle goes to `docs/TODO.md`, blocked on the Settings screen.

**Multi-Image and Iterative Scanning.** For a long or multi-page receipt, the user can pick several images at once (`multiple`), which are sent in one request and synthesized into one extraction. The camera button takes one photo at a time, so a second capture merges into the form rather than replacing it: the frontend extracts what it can, names what is still missing, and a following scan fills only the gaps.

**The camera control is hidden where a camera control does nothing, and the test is `@media (pointer: coarse)` rather than anything about the device.** `capture="environment"` is a *hint the desktop browser ignores*, so on a laptop the two controls are not merely redundant, they are literally the same control rendered twice - both open the same file picker, under two labels promising different things. Three candidate tests, and two of them are wrong. A user-agent string is the usual reflex and is both unreliable and unmaintainable. `navigator.mediaDevices.enumerateDevices()` looks principled and tests the wrong proposition: a desktop with a webcam passes it and still ignores `capture`, because what `capture` addresses is the OS camera *app*, not the presence of a lens. What actually predicts whether `capture` means anything is the input modality, which CSS already answers. So the camera control carries **`pointer-fine:hidden`** and nothing branches in JavaScript - which also keeps this out of the hydration problem `SetupDraftProvider` documents at length, where a value read after mount makes the client's first render disagree with the server's HTML. A touchscreen laptop resolves to `pointer: fine`, because the primary pointer is still the trackpad, and is deliberately treated as a desktop.

**It is written as "hide on fine" rather than "show on coarse", and that is a correctness decision rather than a stylistic one.** The obvious spelling is `hidden pointer-coarse:inline-flex`, and it has two faults. The first is a cascade tie: `hidden` and `pointer-coarse:inline-flex` are both display utilities at equal specificity, so which wins is decided by Tailwind's emission order rather than by the attribute - the same class of failure `frontend/CLAUDE.md` catalogues for paired daisyUI modifiers, and the version of this plan before this revision would have shipped a camera control hidden on **every** device. The second is the fallback. A device answers `pointer: none` when it has no pointing device at all, and then *neither* query matches: "show on coarse" hides the control there, "hide on fine" keeps it. Keeping it is the cheaper failure by a wide margin - a redundant button that opens a file picker, against a phone that has lost the one control this ticket exists for. `pointer-fine:hidden` also puts a single utility in play rather than two, so there is no tie to lose. **The two controls must therefore not differ in `btn` style modifiers**, because a `btn-ghost pointer-fine:btn-outline` would not work: `frontend/CLAUDE.md` records that two style modifiers from one daisyUI component are resolved by the plugin's emission order rather than by the attribute, so ghost wins under every viewport and the variant paints nothing. Both controls are `btn-outline btn-primary`, peers rather than a primary and a secondary, and only visibility varies. Neither competes with the modal's one solid `btn-primary`, which stays on "Add transaction".

**The second control is "Upload receipt", singular, and the singular is the whole point.** It was "Add pages", which is precise and assumes the user already knows the multi-page rule; "Upload receipt" says what the control does to someone meeting it for the first time, and covers a PDF as naturally as it covers photos. **What it must not say is "receipts".** The plural promises a batch import this modal cannot perform: it writes a single `POST /transactions`, so several receipts selected together are synthesized into one transaction with one merchant and one total, silently losing every receipt but the one the model happened to lead with. That is the exact contradiction the previous revision of this plan was written to remove, arriving a second time through the label instead of through the `multiple` attribute. Scanning several distinct receipts into several transactions stays what it was - a different feature needing a review queue, N draft rows and a bulk write - and stays in `docs/TODO.md`.

**PDFs are accepted alongside images, and on a desktop they are the likelier input.** An emailed receipt arrives as a PDF and never becomes a photograph, so the control that replaces the camera on a laptop is most useful pointed at a downloads folder. Gemini reads PDFs natively - no client-side rasterising, no separate parser - which is what makes this cheap enough to include rather than defer. Four consequences follow, and none of them is cosmetic. **Compression has to branch**, because `browser-image-compression` decodes through `createImageBitmap`/canvas and a PDF is not an image to a canvas: PDFs bypass the compression step untouched, which means they arrive at their original size and cannot lean on the 0.75MB the image path guarantees. **So the per-file caps differ**: 1.5MB for an image, 4MB for a PDF. **And the counts differ - at most 4 images, or 1 PDF** - which is what keeps the outer limit strictly the largest, the rule the size stack already had to be corrected for once: worst case is now `max(4 × 1.5, 1 × 4) = 6MB` against the 8mb `bodySizeLimit`, where allowing 4 PDFs would have put 16MB behind an 8mb ceiling. One PDF is not a restriction in practice, because a multi-page PDF already *is* the multi-page case the image path needs four files to express. **And a page is 258 tokens**, so a 40-page bank statement is roughly 10,000 tokens of prompt describing no receipt at all; the 4MB cap is the practical bound on that, and `docs/TODO.md` takes an explicit page-count guard, which needs a parser the backend does not have today.

**The merge tracks which fields the user has touched, not which are empty.** An emptiness test cannot work here, because `AddTransactionModal` initialises `date: todayIsoDate()` - so date is never empty, and a scan carrying the receipt's real date would be refused in favour of today's, with the missing-fields note never flagging it either. The form therefore records a per-field "dirty" set: a scan may overwrite any field the user has not typed into, the pre-filled default date counts as untouched, and anything the user did type is left alone. This is also what makes a second scan safe on a partially typed form.

**Client-side compression.** Mobile phones take large photos (5MB+). Sending these directly wastes bandwidth and slows down extraction. The frontend will compress the image in the browser using the `browser-image-compression` library before POSTing to the backend. This library is chosen because it auto-fixes mobile EXIF rotations (preventing sideways receipt uploads), offloads processing to a Web Worker (keeping the UI smooth), and provides an incredibly simple API for enforcing maximum file sizes. **`useWebWorker: true` is passed explicitly**, because that benefit is a selection criterion and it is not the default.

**Compression can fail, and the format it fails on is the one an iPhone produces by default.** `browser-image-compression` decodes through `createImageBitmap`/canvas, which cannot decode HEIC or HEIF in Chrome or Firefox, and `accept` admits them - so a gallery pick from an iPhone that is not set to "Most Compatible" rejects the promise before any request is made. It is therefore its own outcome with its own copy, naming the format and suggesting the camera control instead - **on a phone**, where that control exists; on a desktop the same copy has to suggest converting the file, since the camera control is hidden there and pointing at it would be advice the user cannot follow. Without this the rejection escapes the handler and the dismissible overlay is the only thing standing between the user and a hang. `maxSizeMB` is also best-effort - the library iterates towards the target and gives up at `maxIteration` - which is the second reason a 413 has to be a real, handled answer rather than a theoretical one. **A PDF never enters this path at all**, and the branch has to be explicit rather than incidental: handing one to `browser-image-compression` is the same canvas rejection as a HEIC, so the client tests the type before compressing rather than compressing and catching.

**Four size limits, layered strictly smallest-innermost, and the outermost is 8mb rather than 6mb for a reason worth writing down.** At most **4** images per scan, **or one PDF**. Each image is compressed to `maxSizeMB: 0.75` with `maxWidthOrHeight: 2000`, which is ample for receipt text; a PDF is not compressed at all, for the reason the PDF decision gives. Multer caps `files: 4`, `fileSize: 1.5MB` for an image and **4MB for a PDF**, so a client that skips compression gets a clean 413 rather than a slow success. The naive outer limit is 4 × 1.5MB = 6MB - but that is *equal* to the inner ceiling, not above it, so multipart boundaries and the Server Action's own payload push a request multer would have accepted over the Next limit first, and the user gets the opaque error instead of the clean one. The outermost limit must be strictly the largest, so it is **8mb**, and the one-PDF rule is what keeps the PDF path under it too. It is also **`experimental.serverActions.bodySizeLimit`**, not a top-level key: in the installed Next 16.2.12 `serverActions` is declared on `ExperimentalConfig`, so the top-level spelling fails `npm run build` - which is this repo's typecheck - and casting past that error leaves the real limit at its 1MB default, which one compressed photo already exceeds.

**`multipart/form-data`, not base64 JSON, and the difference is not cosmetic.** `main.ts` calls `NestFactory.create` with no body-parser options, so Express's default JSON limit of **100kb** applies and any base64 image over roughly 75KB is a 413 before the controller runs. Raising that limit would raise it for *every* endpoint to suit one, weakening the whole API's posture; multer's limits are per-route. Multipart also avoids base64's 33% inflation, which matters when four images share one request. The costs are accepted and both are real: `@types/multer` has to be added (`backend/package.json` has express, jest, node and supertest types and no multer, and `npm run build` is the typecheck, so this is a build failure rather than a warning), and the request body has to be described to Swagger by hand with `@ApiConsumes`, since the plugin cannot infer a file field.

**Multer's limits count bytes, not kinds, so the upload needs a filter and a floor.** `@ApiConsumes` documents a content type and validates nothing, and `limits` caps how many files and how large - so as written, a spreadsheet renamed `.jpg`, or a request with zero file parts, both reach the service and the second one calls Gemini with a prompt and no image, burning quota to be told nothing was found. A `fileFilter` restricted to the MIME types the model actually accepts (`image/png`, `image/jpeg`, `image/webp`, `image/heic`, `image/heif`, `application/pdf`) rejects the first, and an explicit **at least one file** check rejects the second. Both answer 400. Because the caps are now per kind, the filter is also where the mix is enforced: a request carrying a PDF must carry **only** that PDF, and a second part beside it is a 400 rather than a silently dropped file. This is what "400 on a rejected upload" has to mean to be implementable.

**The browser never calls the backend; a Server Action does.** The session is an httpOnly cookie on the *frontend* origin, and `authorizedPost` lifts it into an `Authorization: Bearer` header server-side - so a direct `fetch` from the browser to `POST /api/transactions/scan` gets a 401, whatever the CORS origin says. The scan is a submit from a page the user stays on, which is exactly the split `docs/agents/api-contract.md` draws for a Server Action over a route handler, and it matches `lib/createTransaction.ts`. `lib/session.ts` needs an `authorizedPostFormData` beside `authorizedPost`, since the existing helper serializes JSON.

**`authorizedPostFormData` cannot reuse `AuthorizedWriteResult`, and the reason is the one that type already documents.** `AuthorizedWriteResult` is `{ ok: true } | { ok: false; status?: number }` and carries no parsed body on purpose - its own comment records that the create's body "would have produced a value with no reader". The scan inverts that exactly: the response body *is* the entire point of the call. So the new helper returns `{ ok: true; data: T } | { ok: false; status?: number }`, and `AuthorizedWriteResult`'s comment gains a line naming the scan as the case that finally needed the other shape, so the next reader does not re-derive the argument.

**`gemini-3.6-flash`, via `@google/genai`, on the free tier.** Both names in the first revision were retired: `gemini-1.5-flash` no longer appears in the model list and is unavailable to a fresh key, and `@google/generative-ai` is the legacy SDK, end-of-life since 31 August 2025 and deprecated since 30 November 2025, with a different structured-output API than the maintained `@google/genai`. Of the three current candidates, `gemini-3.6-flash` is the newest stable Flash (since 2026-07-21), accepts image input, supports structured output, has a free tier, and is cheaper on output than `gemini-3.5-flash` ($7.50 against $9.00 per 1M) should this ever go paid - so starting anywhere else would be choosing an older model at a higher price. `gemini-3.5-flash-lite` ($0.30/$2.50) is the documented fallback if free-tier quota bites, accepting lower extraction accuracy for headroom. That is three ids for one call site, which is why the id lives in **one** exported constant rather than inline, and `@google/genai` is a new dependency that has to be added to `backend/package.json`.

**The key is optional, so the endpoint must have a defined keyless answer.** `env.validation.ts` states the contract: "Every variable has a default or is optional on purpose: the backend must still start with no .env at all", which is how CI and the e2e suite run. A `.required()` key would break boot everywhere. `GEMINI_API_KEY` is therefore optional and unpaired, and `/scan` answers **503** when it is absent. The buttons stay visible rather than being hidden behind a capability flag: hiding them would need a new field on a read the modal already makes, and the only environments without a key are CI and e2e, which have no browser. The 503 surfaces as its own message, not as the generic failure.

**`/scan` carries a rate limiter, and adding it means moving the existing registration rather than adding a second one.** `TransactionsController` documents why it has none - "the budget an abuser would burn is their own" - and that reasoning stops holding exactly here, because the budget burned is the project's shared Gemini quota. But `ThrottlerModule` is decorated `@Global()`, so a second `forRootAsync` in `TransactionsModule` would not scope anything: both registrations export the same `THROTTLER_OPTIONS` token, resolution order decides which survives, `AuthModule` is scanned first, and a `scan` throttler that lost the race is silently *absent* from the resolved options - leaving `/scan` with no limit at all while every gate stays green. **This is the same silent-skip class of bug the repo already hit with a bare `@SkipThrottle()`**, arrived at from the opposite direction. So the one registration moves to `AppModule` and gains a **third** named throttler, `scan`, keyed on the session user id rather than on IP - `SessionGuard` is a global `APP_GUARD` and Nest runs global guards before controller-scoped ones, so the principal is on the request by the time the tracker reads it, and a NAT would otherwise share one bucket. Limit and window are configuration for the reason `AuthModule` gives, so a spec can trip them without waiting out the window.

**Naming the throttlers is not enough; every route must skip the ones that are not its own.** `ThrottlerGuard` runs *every* configured throttler on the route it guards, so once `scan` is registered globally the existing auth limiters apply to `/scan` too. That is not a harmless extra: `trackByEmail` reads `req.body.email`, guards run before interceptors, so on a `multipart/form-data` request `req.body` is undefined and it falls back to `trackByIp` - which `auth.module.ts`'s own PET-11 note says resolves to the *frontend server's* address for every user in production. `/scan` would inherit a single global bucket of the auth limit shared by everyone. So `/scan` gets `@UseGuards(ThrottlerGuard)` with `@SkipThrottle({ email: true, ip: true })`, and `AuthController` gets `@SkipThrottle({ scan: true })`. Both directions are required; either one alone leaves a route running a limiter written for a different shape of request.

**What the scan limiter actually protects, stated honestly.** It does **not** cap total consumption of the Gemini quota, and the plan should not claim it does. `backend/.env.example` already records that the throttler store is in-memory - so on more than one Fly machine each user gets a full bucket per machine - and a per-user limit is per-user by construction: N users each sitting at their limit still exhaust a shared free-tier quota. What it buys is fairness and blast radius: one account in a retry loop cannot outrun everybody else, which is the realistic failure for an app whose users are all test accounts. A genuine aggregate cap needs a shared store and a global counter, and that goes to `docs/TODO.md` rather than being implied here.

**The call is bounded, and the modal can always get out.** A hung or quota-throttled Gemini call would otherwise leave the loading overlay up forever, which is the failure PET-56 was an entire ticket about. The request carries an abort signal with an explicit timeout, a timed-out scan answers **504** so it is distinguishable from the keyless 503 rather than collapsing into it, and the overlay is dismissible while a scan is in flight.

## Shape

`docs/explainers/receipt-scanning-modal-preview.html` draws all of this - the two control rows, the three states that differ, and every outcome in the table below - in stock daisyUI on the app's own themes, pinned to the installed daisyUI, Tailwind and lucide exactly as its sibling pages are. It is the sign-off artifact for the questions this section leaves to a designer, and opening it in a browser is the whole procedure. Note it draws `modal-box` **outside** an open `.modal`, which costs three utilities the real component must not carry; that file's own comment says which and why.

**The Frontend:**
- Two inputs inside the `AddTransactionModal`, both routed through one handler, and on a desktop only the second is drawn:
  - "Scan receipt" (camera): `<input type="file" accept="image/*" capture="environment">`, carrying `pointer-fine:hidden` so it disappears where `capture` means nothing.
  - "Upload receipt" (files): `<input type="file" accept="image/*,application/pdf" multiple>`, for a receipt too long for one photo or one that arrived as a PDF. At most 4 images, or 1 PDF.
- Both are `btn-outline btn-primary`, peers rather than a primary and a secondary, so no `btn` style modifier has to vary by viewport.
- **After a successful scan the two labels become "Scan again" and "Add pages"**, because the second scan is a different act from the first: the first offers to read a receipt, the second offers to fill the gaps in what was read, and "Upload receipt" over a form already holding a merchant and a total reads as an offer to start over. This is the one place "pages" survives as a label, and it is correct there - by then the user has seen the multi-page rule work.
- A short disclosure line beside them naming what leaves the device and what is not kept.
- A loading state that overlays the modal while the extraction runs (typically 3-5 seconds), dismissible, with a timeout behind it.
- Once the extraction API responds, the returned fields are merged into form state for every field the user has not typed into, the default date included.
- A note naming any field the extraction did not fill, `date` and a dropped `categoryId` among them, encouraging another photo to fill the gaps.

**Every outcome has copy, and the statuses and the copy are one table rather than two lists:**

| Outcome | Source | Copy names |
| --- | --- | --- |
| Fields extracted, some missing | 200 with a non-empty `missing` | which fields to photograph again |
| Nothing extracted | 200 with every field null | that the photo was unreadable |
| Scanning unavailable | 503, no API key | that scanning is off, not that the scan failed |
| Rate limited | 429, over the per-user limit | that it is temporary, and roughly how long |
| Extraction timed out | 504, abort fired | that it timed out, and to retry |
| Upload rejected | 400, wrong type, zero files, or a PDF sent beside other files | what it accepts: photos, or one PDF |
| File too large | 413, past multer's cap | which cap was passed - 1.5MB an image, 4MB a PDF |
| Compression failed | client-side, before any request | the format (HEIC), and the camera control on a phone or converting the file on a desktop |

**The Backend:**
- `POST /api/transactions/scan`, on `TransactionsController`, above `@Get(':id')` - which now has a literal sibling, so the route-order note in that class comment becomes a real constraint rather than a warning.
- Accepts `multipart/form-data` with 1-4 image parts, **or exactly one `application/pdf` part**. No base64 branch.
- A `fileFilter` restricted to `image/png`, `image/jpeg`, `image/webp`, `image/heic`, `image/heif`, `application/pdf`, an at-least-one-file check, and a rejection of a PDF sent beside anything else. All answer 400.
- A `ScanReceiptResponseDto`: `merchant`, `amount`, `date`, `categoryId` and `note`, each null when not extracted, plus a `missing` array naming the fields that are.
- Uses the **Google Gemini API (via Google AI Studio)** on `gemini-3.6-flash` through `@google/genai`, with structured output enforcing the response schema.
- Fetches the user's categories and their **top 50 merchants of the past year** by transaction count, with the categories and counts attached, in one query. This contextual data is injected into the AI prompt to maximize categorization accuracy.
- Validates all three invented values: `categoryId` against the user's live categories, `date` as a real ISO calendar date, `amount` as a positive number. Anything that fails is dropped and reported in `missing`.
- 503 with no API key, 504 on timeout, 429 over the per-user limit, 400 on a rejected upload, 413 over the size cap.

## Verification

From `backend/`: `npm run lint`, `npm test`, `npm run test:e2e` and `npm run build`. From `frontend/`: `npm run lint`, `npm test` and `npm run build`. From the repo root: `npm run docs:check` and `npm run api:sync` (which must leave no diff).

Then the app itself. Steps 2 and 5 are the only ones that need a real phone: `capture="environment"` does nothing in desktop Chrome, so the ticket's actual subject goes unverified there. Steps 13 to 15 are the desktop half and must be run in a real desktop browser, not a narrowed one - DevTools device emulation changes the viewport and can be made to report a coarse pointer, so it can show the phone layout on a machine where `capture` would still do nothing. **Step 13 is the one no automated check can stand in for**, and this is worth stating because it was tried: headless Chromium reports `pointer: none`, never `fine`, so it can prove the control *appears* but never that it disappears. A `pointer: coarse` probe demonstrates the utility beats daisyUI's `.btn` display, which leaves only "does this desktop report `fine`" - and that is exactly what step 13 looks at.

1. Open the "Add Transaction" modal on a phone.
2. Tap "Scan receipt", photograph a receipt, and verify the camera opens rather than a file picker.
3. Verify the loading state appears and can be dismissed.
4. Verify Merchant, Amount, Category, Date and Note populate, that Date is the receipt's date rather than today's, and that Amount reads with two decimals exactly as an edited amount does.
5. Type a merchant by hand, scan again, and verify the typed merchant survives while the untouched fields update.
6. Photograph only the top half, verify the note names the missing fields, then photograph the bottom half and verify they fill in without clearing the form.
7. Select two pages of one long receipt together and verify they are synthesized into one extraction.
8. Submit the transaction and verify it saves.
9. Scan past `SCAN_RATE_LIMIT` within the window and verify the 429 renders its own message - then immediately request a login link and verify the auth limiter is untouched by the scanning.
10. Restart the backend with `GEMINI_API_KEY` unset and verify the 503 renders its own message rather than the generic failure.
11. Upload a file that is neither an image nor a PDF and verify the 400 names what is accepted.

15. Upload a PDF over 4MB and verify the 413 names the PDF cap rather than the image one, then send a PDF together with a photo and verify the 400 explains the mix.
